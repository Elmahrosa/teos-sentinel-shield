Core Components

Service Architecture

The TEOS Sentinel ecosystem consists of six primary services.

Sentinel Shield API
Express API gateway handling authentication, rate limiting, billing, and routing scan requests to the risk engine. Provides SSE streaming for live dashboard events.
Node.js · Express · Upstash Redis · Supabase · Dodo Payments
Risk Engine (MCP)
Deterministic risk classification engine with 27 named rules across 8 categories. Supports code/shell, CI/CD, and dependency scanning. Model Context Protocol interface for AI agent integration.
TypeScript · Express · Regex Engine · Prometheus Metrics
Activation Service
Hybrid CQRS/event-sourced license activation service. Manages product key validation, credit tracking, and tier enforcement.
Node.js · Event Sourcing · Railway
TEOS Bot
Telegram bot providing scan, dependency check, and CI/CD audit commands. Routes requests through the MCP API and activation service for credit management.
Telegraf · Telegram API · Railway
WebSocket Server
Railway-deployed WebSocket server serving static front-end assets and providing real-time communication for the SOC dashboard.
ws · Express · Railway
Landing Site
Next.js marketing site deployed on Hostinger. Features Egyptian-themed sentinel landing page, pricing tiers, and transparency hub.
Next.js · Hostinger · GitHub Pages
Scan Flow

Request Lifecycle

How a scan request flows through the system.

  1. Client Request — Code is submitted via API (REST/Telegram/MCP)
  2. Authentication — Sentinel API validates API key and checks rate limits via Upstash Redis
  3. Credit Check — Activation service verifies available credits for the requester's tier
  4. Deterministic Scan — Risk Engine matches input against 27 named rules (regex-based, 8 categories)
  5. Heuristic Analysis — Additional suspicion scoring via heuristic engine (7 signals)
  6. Verdict Assembly — Combined deterministic + heuristic result: ALLOW / WARN / BLOCK with score 0–100
  7. Audit Logging — Structured audit entry written to Supabase Postgres and NDJSON file
  8. Billing Event — Credit consumed via activation service; Dodo Payments webhook for subscription plans
  9. Response — Verdict, score, matched rules, and reasons returned to client
Rule Categories

Deterministic Rules

The engine comprises 27 named rules organized into 8 security categories. Each rule has a fixed risk score and severity level. The maximum matched rule score determines the verdict (BLOCK ≥ 85, WARN ≥ 40).

CategoryRulesExample Patterns
Shell CommandsR01–R03, R06, R08, R13rm -rf, chmod 777, fork bomb, reverse shell, sudo abuse
SecretsR04, R05, R07, R19echo $SECRET, env exfil, hardcoded keys, tokens
SQL InjectionR09, R10DROP TABLE, UNION SELECT, OR 1=1, SQL comments
Supply ChainR14, R15Known malicious packages, typosquatted names
CI/CDR16, R17, R18, R25write-all permissions, curl|bash, privileged containers
NetworkR21, R22SSRF to metadata endpoints, SSH key exfil
MalwareR23, R24Cryptominers, data exfiltration via curl/nc
OtherR11, R12, R20, R26, R27Path traversal, command injection, prompt injection, base64 exec, XXE
